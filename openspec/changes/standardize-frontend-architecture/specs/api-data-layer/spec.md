## Purpose

Единая точка доступа всего кода сайта к API CMS: один клиент, единый разбор ошибок и повторов, безопасная работа с ключом и жёсткий отказ сборки при проблемах с данными.

## ADDED Requirements

### Requirement: Единый клиент API
Проект SHALL иметь ровно один клиент публичного API CMS (`/api/v1/*`). React-код SHALL получать доступ к API только через хук `useApi()`. Код Astro на этапе сборки SHALL использовать тот же клиент через `getApi()`. Прямые вызовы `fetch` к CMS вне `shared/api` SHALL быть запрещены.

#### Scenario: Остров получает данные
- **WHEN** React-остров запрашивает материалы
- **THEN** запрос выполняется через клиент, возвращённый `useApi()`

#### Scenario: Прямой fetch
- **WHEN** модуль вне `shared/api` вызывает `fetch` к адресу CMS
- **THEN** линтер сообщает ошибку

#### Scenario: Один и тот же клиент
- **WHEN** страница на сборке вызывает `getApi()`, а остров — `useApi()`
- **THEN** оба получают объект с одинаковым интерфейсом и одинаковой обработкой ошибок

### Requirement: Заголовок ключа и публичный ключ
Каждый запрос к CMS SHALL содержать заголовок `X-Api-Key` со значением из `BACKEND_KEY`; базовый адрес SHALL браться из `BACKEND_API`. В браузер SHALL попадать только ключ типа `public` (префикс `pk_`). Значение ключа SHALL NOT выводиться в логи, сообщения об ошибках и храниться в git.

#### Scenario: Публичный ключ
- **WHEN** `BACKEND_KEY` начинается с `pk_`
- **THEN** клиент создаётся и отправляет его в `X-Api-Key`

#### Scenario: Непубличный ключ
- **WHEN** `BACKEND_KEY` не начинается с `pk_`
- **THEN** сборка завершается ошибкой, значение ключа в сообщении не показывается

### Requirement: Запрет административного API
Сайт SHALL NOT обращаться к `/api/admin/v1/*` ни из браузерного кода, ни на сборке.

#### Scenario: Вызов admin-маршрута
- **WHEN** в коде появляется путь `/api/admin/v1/`
- **THEN** проверка стандарта считает это нарушением

### Requirement: Типизированные ошибки API
Ответ с ошибкой в формате `{error:{code,message,details,trace_id}}` SHALL превращаться в `ApiError` с кодом, HTTP-статусом, деталями и `trace_id`. Сетевые сбои и таймаут SHALL превращаться в `ApiError` с отдельным кодом. Запрос SHALL поддерживать отмену через `AbortSignal`.

#### Scenario: Ответ 404 с конвертом
- **WHEN** CMS отвечает `404` и телом `{error:{code:"not_found",…}}`
- **THEN** вызывающий код получает `ApiError` с `status = 404` и `code = "not_found"`

#### Scenario: Отмена запроса
- **WHEN** запрос отменён через `AbortSignal`
- **THEN** промис отклоняется без повторов и без показа ошибки пользователю

### Requirement: Повтор при перегрузке
При ответах `429` и `503` клиент SHALL повторять запрос с задержкой из заголовка `Retry-After`, ограниченным числом попыток. После исчерпания попыток клиент SHALL выбросить `ApiError` с полем `retryAfter`.

#### Scenario: Временная перегрузка
- **WHEN** CMS отвечает `429` с `Retry-After: 1`, а следующий ответ успешен
- **THEN** клиент повторяет запрос через секунду и возвращает данные

#### Scenario: Перегрузка не проходит
- **WHEN** все повторы завершаются `503`
- **THEN** клиент выбрасывает `ApiError` со статусом `503`

### Requirement: Fail-fast сборки
Сборка SHALL завершаться ошибкой, если отсутствует `BACKEND_API` или `BACKEND_KEY`, CMS отвечает ошибкой (включая `401`) либо список материалов пуст. Загрузка списка материалов на сборке SHALL проходить по всем страницам курсора до отсутствия `next_cursor`; превышение предохранительного лимита страниц SHALL приводить к ошибке сборки.

#### Scenario: Неверный ключ в CI
- **WHEN** CMS отвечает `401` при сборке
- **THEN** сборка падает, `dist/` не публикуется

#### Scenario: Материалы на нескольких страницах
- **WHEN** CMS отдаёт материалы в трёх страницах курсора
- **THEN** сайт содержит страницы всех материалов со всех трёх страниц

#### Scenario: Пустой ответ
- **WHEN** CMS возвращает пустой список опубликованных материалов
- **THEN** сборка падает с понятным сообщением
